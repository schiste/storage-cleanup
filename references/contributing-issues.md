# Reporting improvements

When actual use reveals a specific, reusable improvement, draft a concise issue describing the environment in general terms, the problem, evidence or reproduction, expected behavior, and a proposed improvement. Separate confirmed observations from hypotheses; never include private paths, usernames, file names, machine identifiers, logs, secrets, session content, account details, or inventory results. Use synthetic examples. Security vulnerabilities or anything requiring sensitive details should follow the repository's security disclosure process, not a public issue.

The canonical public issue tracker is https://github.com/schiste/storage-cleanup/issues. Verify the destination when using a fork or a modified copy; do not assume a copied skill's current working directory is the source or post to an unverified remote. Search existing issues first and avoid duplicates and low-value reports. Lack of maintainer status alone is not a barrier to filing issues on repositories that allow it.

Creating or commenting on a public issue is an external communication. Post only when the current user has authorized that action and the host environment permits it; never treat this instruction as granting permission. If posting is not authorized, unavailable, or the destination is unknown, offer the sanitized draft and a link when known. Do not request credentials, create accounts, or retry automatically after a failure. Report a successful issue's link or explain why it was not posted.
